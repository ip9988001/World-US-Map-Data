## P5 · Overture 县片上游限流秒败，整县永久缺片 ✅

**现象**：WA 有 11 个县的 Overture 切片在 **4.2 秒内全败**（`overturemaps` CLI 秒退），原代码一次不中就记死。

**根因**：连发查询撞上游 STAC/S3 限流，CLI 立即返回非零退出；原代码无重试。

**处置**：两轮修复
- `5906bae`：退避 15s/30s，最多重试 3 次（确认为空县时不重试）
- `1d663c5`：改「同片退避 + 尾片补卷」，失败时带出 stderr 尾

**证据**：run 里的 `1446:25–14:48:33 连续上传 28 片，14:48:35–14:48:39 的 4.2 秒内 11 个县全部失败`。

## P6 · 大州州级全量主键枚举必撞 350 分钟上限 ✅

**现象**：MA 跑 5 小时零产出；AZ 州级枚举 3h10m 仍在跑；两者最终都撞 `timeout-minutes: 350`。

**根因**：`ids + county_shards` 模式下州 bbox 的 OID 区间二分枚举是**无条件执行**的。AZ 366 万行单次 count 要 56 秒且常被 400，全量枚举 3h+；MA 门牌量 512 万更大。

**处置**：`0aee8e6` —— 新增 `--skip-state-ids {auto,always,never}`，默认 auto：先做一次州级 count 探针，≥200 万行就走县口径跳过枚举；count 拿不到（400/超时）按大州处理。

**代价**：不产 OUTOFSTATE 溢出包、不做州级三数咬合（`three_number_check.applicable=false` 如实声明）。

**证据**：`raw-US-MA-v1` 5 小时 0 资产；AZ run 39553902621 的 3h10m 枚举。

## P7 · partial 补跑 exit 5 被显示成 failure 🟡

**现象**：AZ 补跑 04013/04019 完全成功（四源 ok、门禁通过、69 产物 1183 MB），但 run 显示 `failure` —— 因为脚本主动 `exit 5` 拒绝封印。

**根因**：GitHub 把任何非零退出码当失败，而 exit 5 是"设计性拒绝"。

**影响**：告警噪音，人需人工判断"这是成功还是失败"。

**处置**：**未修**。建议把 exit 5 在 workflow 里映射成 neutral / success-with-notice。

**证据**：run 39584159627 日志尾部「本轮为『只补指定县』模式：县片已上传，但拒绝封印」。

## P8 · STATUS.done / counties_done 只反映本轮，不合并历史 🟡

**现象**：GA 的 STATUS `done=['13089','13121','OUTOFSTATE']`、`counties_done=2`，但 release 里资产 478 个。

**根因（待确认）**：partial 补跑写 STATUS 时，`done`/`counties_done` 按**本轮**统计，未与历史合并。

**影响**：后续 partial 补跑会基于不准的 done 判断续传，可能重复抓或漏抓；`pipeline_audit` 的「缺县」判断也会被误导。

**处置**：**待验证**。需对比同一州多次 partial 前后的 STATUS.done 变化确认。

## P9 · 哨兵发现问题就把 run 弄红，真假难辨 ✅

**现象**：`pipeline-audit` / `run-watch` / `content-audit` / `preflight-upstream` 发现异常即 `exit 1`，run 列表一片红。

**根因**：告警语义与健康语义混用——「我发现了问题」和「我自己坏了」都是红。

**处置**：`586490a` 改 exit 语义——问题交给 Issue 表达，run 保持 success；只有脚本异常/取数失败才非零。

## P10 · 看门狗把新建 workflow 判成停摆 ✅

**现象**：Issue #1「🔴 哨兵停摆」把 `preflight-upstream` / `content-audit` 判红，但它们当天才建、首次 schedule 未到点。

**根因**：看门狗按「从未运行」直接判死，无宽限期。

**处置**：`586490a` 新建 workflow 24 小时宽限期。

## P11 · 收信箱只在新信时唤醒，已投递的永远不处理 ✅

**现象**：Issue #1/#2 已投递（seen 里记着），此后每 2 分钟只打印"无新信"，队列里那 2 条永远没人处理。

**根因**：唤醒条件写的是"本轮有新信"，而不是"队列里有待处理"。

**处置**：改为「只要 pending 非空且无锁就唤醒」。
