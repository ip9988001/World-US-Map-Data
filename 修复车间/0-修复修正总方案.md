## 三、修复方案（待确认后执行，按依赖排序）

### S1 · 账本单一入口（治 B1/B2/B3/B4/D6）
- 所有资产上传成功后，**立刻**写一条记录到统一账本（`fx.meta` + `STATUS.assets` + `MANIFEST.assets` 同源生成）
- MANIFEST 生成时以「记账 ∪ 实物（磁盘 ∪ 已上传）」为准，任一来源有就写进去
- shards 同理：`nad_shards` ∪ `STATUS.assets(kind=county)`
- **验收**：任取一个 Release，`len(manifest.assets)` == Release 资产数 − 3（MANIFEST/STATUS/RELEASE_NOTES）；shards 数 == 实物 NAD 片数

### S2 · 历史 28 州账本回补（治历史带病，不动数据）
- 用 `S1` 的同一套逻辑写一个 `scripts/manifest_reheal.py`（一仓版，仅修账）
- 对 28 个 Release 逐个：拉实物清单 → 补 shards/assets → clobber 上传 MANIFEST.json
- **验收**：8 个漏记州全部归零；AK 的 shards = 23 且 rows 合计 325,379

### S3 · 5 个半成品州善后（治 D5）
- MD / OK：无任何数据 → 删 tag 重跑（0 成本）
- KY / NE / NM：NAD 县片已在 → **续跑补 OV/OA/TIGER**（不重抓 NAD，省数小时）
- 前置：必须走 S1，否则补完还是漏账
- **验收**：5 州 phase=complete + 四源齐 + 账实一致

### S4 · 处置器收紧（治 D3/D4）
- `agent_fix.py` 的 cancel 条件改为：`in_progress > 2h` **且** 连续 3 次巡检（15min/次）无新日志/新资产
- cancel 后必须**自动重跑同参数 run**，并在哨兵广播「已取消 + 已重跑 <run_id>」
- 黄条不改代码、不动 run，只记录
- **验收**：人为造一个 8 分钟的慢 run，处置器不得取消

### S5 · 一仓交付契约冻结（治 E1/E2）
- 写成 `docs/交付契约.md` 并进 gate 自检：
  - NAD：必须 `NAD-US-<ST>-<fips>-<key>.ndjson.gz`，一县一片，行数 = 官方县级 count
  - Overture：**是否一律按县**（待你拍板）
  - OA：保持源文件粒度（上游本身就是按源分包，不切）
  - TIGER：addrfeat 按县、边界 geojson 按县
  - MANIFEST 必含：shards / assets / completeness / reference_check / row_counts
- **验收**：gate 能在跑前校验命名与粒度

### S6 · 剩余 23 州铺开（S1~S5 通过后）
- 顺序：小州 → 大州（先暴露问题）
- 每州跑完自动核验：四源齐 + 账实一致 + 行数咬合，任一不过不进封印
- **验收**：51/51 州 phase=complete

## 五、风险与取舍

| 风险 | 说明 | 应对 |
|---|---|---|
| 回补账本动到 MANIFEST | 内容变了，`integrity.sha256` 若覆盖自身会失配 | 回补时重算 integrity，或明确 integrity 只覆盖数据资产 |
| Overture 全州按县切片 | IA 99 县 → 99 个小 parquet，上传次数 ×100 | 需先测 Actions 时长与 API 限额 |
| 续跑 KY/NE/NM | 断点续传会跳过已有 NAD，但可能再次漏账 | 必须先落 S1 |
| 删 MD/OK tag | tag 删了不能恢复（数据为 0，无损失） | 直接删 |
